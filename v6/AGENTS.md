# AGENTS.md — pipeline rules

This directory is built as a one-directional pipeline. Human authors only the two
top layers; everything below is generated.

```
✍️ human, independent atoms            🤖 agent (human reviews)        🤖 read-only
user-story/*.md   ─┐
                   ├─► spec/<behaviour>.md  ─►  src/*.py (+ tests)
dev-requirements/  ┘     1 file = 1 behaviour      module = union of
*.md                                               all behaviours
```

## File discovery

There is **no index/manifest** of files. To process a layer, **walk its directory tree**
and discover every file, preserving hierarchy. Subfolders are allowed for grouping and
are part of a file's identity along with its name.

## Layers

### user-story/
- The end user is **a programmer**. Each file is **one atomic story** describing how
  that programmer wants to use the feature, what result they expect, and (optionally) a
  rough description of the algorithm/behaviour.
- Should include a **usage example** (how it is declared/called) and the **expected
  result**.
- **No links of any kind** — not to dev-requirements, not to other user stories.
  A story must stand entirely on its own.
- **Identity lives in the filename** (self-describing kebab-case). No header/ID block.
- Must contain **acceptance criteria** — these are the source of truth for tests.

### dev-requirements/
- Holds **only technical details**: which tools/libraries to use, how to test,
  architecture and patterns, conventions. These are typically cross-cutting and shared
  across many stories — not per-feature behaviour (behaviour lives in user-story).
- Each file is **one standalone technical concern**.
- May link **only to other dev-requirements** (DR↔DR). Never link up to a user story.
- **Identity lives in the filename.** No header/ID block.

### spec/
- **Generated by the agent, reviewed by the human.** Never authored from scratch by
  the human.
- Produced by sweeping over **all** user-stories and **all** dev-requirements, one by
  one, and synthesising behaviour. The US↔DR connection exists only here, at
  generation time — it is never recorded in the source files.
- **Granularity: one file = one coherent behaviour** (may span several src modules).
- **Identity lives in the filename.** No header/ID block.
- Must be formal enough that the implementation is almost mechanically derivable.

### src/
- **Read-only artefact. Never hand-edited.** To change behaviour, change the spec and
  regenerate.
- Because spec→src is many-to-many, **regeneration is holistic**: to rebuild a module,
  read every spec file that touches it — a module is the union of its behaviours.
- Ships with tests derived from user-story acceptance criteria.

## README.md

`README.md` is the human-facing guide to the library — written for the programmer who
*uses* it, not for someone editing the pipeline (that's this file, AGENTS.md).

- **Generated, read-only**, like `src/`. Never hand-edited — change the stories and
  regenerate.
- **Source is `user-story/`**: it presents each story's usage example and expected
  result, grouped into a readable narrative. It must not introduce usage absent from the
  stories.
- Structure: short intro → install/setup → one section per capability (taken from the
  stories) with a runnable example → link onward to deeper docs if any.
- It describes only stable, user-facing behaviour. Internal/technical detail
  (dev-requirements) and unresolved open questions in spec are out of scope.

## Generation procedure

1. **req → spec**: sweep all `user-story/` and `dev-requirements/`. Synthesise one
   spec file per coherent behaviour. A spec must not introduce behaviour absent from
   the stories/requirements. Stop here for human review.
2. **spec → src**: regenerate affected modules holistically from the full spec set.
   For every user-story acceptance criterion, emit a test.

## Definition of Done

- All tests derived from acceptance criteria are green.
- Regeneration is idempotent: re-running with unchanged spec produces unchanged src.

## Integrity checks

- No user-story contains a link.
- No dev-requirement links to a user story (DR↔DR only).
- Every behaviour in spec is traceable, by reasoning, to at least one US and the DRs
  it must honour (the reasoning is shown in the review, not stored in files).
- `src/` has no hand-edits (verified via `git diff` after regeneration).
